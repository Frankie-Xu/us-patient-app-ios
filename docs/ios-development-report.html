02 / PRODUCT BOUNDARY

围绕一次就诊，而不是平铺所有健康数据

第一版的成功标准是交付一份资料包并在第二次就诊时被再次使用。

用户与任务

患者

上传中文/英文材料，核对关键事实，设置本次就诊目的，生成并分享准备包。

照护者

在明确授权的主题或就诊包范围内补充材料、协助核对、查看待办。

接诊方

打开患者主动分享的只读版本，查看来源，下载 PDF；默认不能写回患者库。

协调人员

处理获授权病例、发起补件、标记交付、记录人工校核；每次访问进入审计日志。

范围纪律

首版做

  • PDF/照片导入、OCR、原件和版本保留。
  • 中英事实抽取、来源索引、冲突和缺口状态。
  • 患者版/医生版摘要、最多 3 个优先问题、待办。
  • 过期/撤回分享链接、PDF、基本访问审计。

首版不做

  • 诊断、风险分层、治疗/处方建议和影像判读。
  • 自动修改或写回 EHR/临床记录。
  • 全量穿戴数据、检测商城、补充剂或交易链。

R18设置本次目的可编辑就诊目标。
R19生成患者摘要使用可理解语言。
R20生成医生摘要结构化且可追溯。
R21问题清单最多 3 个优先问题。

22–28 · 分享与控制

R22生成 PDF 报告版本和来源索引。
R23只读分享链接默认最小内容集。
R24过期与撤回显示边界与状态。
R25访问日志谁、何时、哪个版本。
R26待办与提醒来源、负责人、日期。
R27照护者协作首版限受邀代管。
R28导出与删除结构化数据与清除。

共性验收：每条需求都要有空状态、失败状态、来源/权限边界和可测试完成条件。不能用“AI 会自动处理”代替验收描述。

04 / IOS EXPERIENCE

导航围绕就诊任务组织

以下是适合首发的客户端信息架构和屏幕职责；最低 iOS 版本、离线范围和账号方式仍是 Wayfinder 决策。

Home当前预约与变化新记录、待确认、下一步；不堆健康数据。
Records文件、原文、版本上传、筛选、打开原件；每个事实可回到页码。
Topics按就医问题聚合相关文件、事实、变化和缺口进入同一问题。
Review变化与冲突逐项确认、补充患者自述、处理低置信字段。
Visits目的、摘要、问题生成 For me / For my doctor 两种视图。
Share版本与访问状态选择内容集、有效期、撤回；默认只读。
Tasks待办与下一次负责人、日期、来源、完成依据持续到下次。
Settings语言、同意、导出、删除解释数据如何使用；不把 AI 草稿标成医生确认。

统一状态机

draft初始整理
→
needs review缺口 / 冲突 / 低置信
→
confirmed患者或授权审核者确认
→
shared指定版本可访问
→
revoked / archived停止后续访问

关键交互规则

  • 患者自述、原始记录、人工修改和 AI 整理结果分层展示。
  • “未提供”不等于“没有”；“待确认”不等于“异常”。
  • 药物当前状态、否定表达、单位和日期不能由客户端或模型猜测。
  • 提交分享前显示草稿/已确认状态和来源覆盖提示。

工程建议 · iOS 基线

  • SwiftUI + Observation/MVVM；按 Home、Records、Review、Visits、Tasks 拆 Feature。
  • Swift Concurrency + URLSession；上传、轮询、重试和状态变化统一由用例层管理。
  • PhotosUI / PDFKit 负责选择与预览；服务端负责 OCR 与事实抽取。
  • Keychain 保存令牌；原件使用受保护文件存储，服务端作为事实与版本的唯一来源。
需由 iOS 基线票确认

建议的依赖方向

  • View → Feature ViewModel → Domain UseCase → Repository。
  • Repository 通过协议访问 API、缓存和文件；屏幕不直接拼装请求。
  • Domain 不依赖 SwiftUI；便于单元测试与后续网页/协调端复用。
  • 所有写操作返回新版本或状态事件，客户端以服务端版本为准。

后台任务

上传可暂停/重试；OCR/摘要采用异步作业状态，App 回前台时刷新；不得把长任务的完成仅依赖一个进程内回调。

06 / AI QUALITY & SAFETY

AI 输出必须可追溯，也必须会停下来

质量契约是产品能力的一部分；没有来源、无法解释或出现高严重度错误的内容不得进入医生版默认交付。

导入原件与版本
OCR / 布局文字、表格、页码
事实抽取药物、过敏、日期、检查
冲突检测并列展示出处
人工/患者核对再生成、再分享
≥98%关键字段 precision

药物、过敏、日期、检查结果及其状态。

≥95%关键字段 recall

在标注集内不遗漏高价值事实。

≥95%出处覆盖率

摘要事实都能跳回页码或来源。

0未标记高严重度错误

任何此类错误都阻断交付并进入回归集。

硬性输出规则

  • 每条事实必须带 source_ref，或明确标为 user_input。
  • 缺失信息输出“未提供”；冲突信息并列展示。
  • 疑似/待排/历史用药不得改写成确诊/当前用药。
  • 翻译保留医学缩写、否定词、单位和原文；低置信内容要求确认。
  • 问题清单只能来自用户目标、原记录未决事项或已有随访要求。

回归与人工复核

  • 建立覆盖扫描件、表格、双语、否定表达、日期冲突的 30–50 例去标识金标准。
  • 两位合格审核者独立标注；分歧进入仲裁与回归集。
  • 模型、OCR 或提示词变更都重跑关键指标与高严重度错误清单。
  • 记录人工查证时长、改写比例、拒绝率和每例成本。

输出契约：摘要段落至少绑定 claim_id · source_ref · source_type · confidence · review_status。没有来源或无法解释的内容不进入“医生版”默认内容。

07 / TRUST & CONTROL

把分享当成版本化交付，而不是把病历库发出去

患者控制当前就诊包的内容、有效期和撤回；任何下载或复制边界都要在产品中明确说明。

角色权限矩阵

角色可见内容可执行动作默认限制
患者全部原文、事实、摘要与日志核对、编辑自述、生成/撤回分享不能把 AI 草稿标成医生确认
受邀照护者授权的主题或就诊包补充材料、协助核对、看待办不可扩大授权
接诊方主动分享的只读版本看来源、下载 PDF默认无患者库写入权
协调人员获授权病例与交付状态补件、标记交付、记录校核每次访问入审计日志

上线前必须锁定

  • 真实服务主体、数据流、合同和部署区域。
  • 认证强度、接收方身份验证、链接有效期默认值。
  • 删除、导出、撤回、日志访问和泄露响应路径。
  • 原件、派生事实、摘要版本和人工修改的保留策略。
  • 本地缓存是否允许存在，以及设备丢失时的清理策略。
合规票 02 未关闭前不能宣称已满足法规

PRD 已明确产品定位为资料整理、就诊准备和交付工具；这不等于自动满足 HIPAA、FTC 或州隐私法。上线前应按实际服务主体、数据流、地区和合同关系做正式审查。

按可验证出口推进，而不是按页面数量推进

时间是建议值，团队可按人数和服务端成熟度调整；每阶段都要有可演示、可测试的出口。

Phase 0 · 决策冻结

Definition of Done

产品

  • 主流程有空、加载、失败、重试、成功和撤回状态。
  • 患者版与医生版明确区分，状态与来源可见。
  • 每个需求均有可操作的验收步骤。

工程

  • 网络失败、重复提交、过期版本和并发更新可恢复。
  • 所有写操作具备幂等键或版本校验。
  • 日志不泄露病历正文；敏感字段分级记录。

评测

  • 关键字段 precision/recall、出处覆盖率和高严重度错误清单通过。
  • 医生能在 90 秒内找到指定事实并回到原文。
  • 记录人工分钟、返工率、拒绝率、成本和付款。
09 / RISKS & NEXT DECISIONS

开发启动前的检查表

这些不是泛化的风险清单，而是会直接改变客户端、接口或试点结果的事项。

资料质量

扫描件、缺页、不同单位和不同日期会放大错误。原件保留、缺口提示、版本和人工复核必须一开始就存在。

事实错误

把历史用药写成当前用药属于高严重度风险。来源契约、冲突阻断和回归集是发布门禁。

信任与合规

用户必须理解 AI 整理、分享、撤回和下载副本的边界；服务主体和数据处理协议不能留到上线后。

单位经济

补件、翻译、审核和支持可能高于模型成本。每例记录人工分钟、返工率和实际付款。

Go / Pause / No-go

GO

关键字段达到目标；医生能在 90 秒找到指定事实；出现复诊用户和真实付款。

PAUSE

摘要仍需大量重写、材料缺口无法解释，或每例人工成本超过价格假设。

NO-GO

出现未标记高严重度错误、未经授权访问，或用户无法理解分享与撤回边界。

下一步建议
